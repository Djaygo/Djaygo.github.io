## What If the Schema Was the Whole Thing?

Most document processing code is glue. You write a parser for this format, a normalizer for that one, custom extraction logic for every new document type. I wanted to flip that: what if you just defined a schema and a prompt, and the pipeline handled routing your document through OCR and an LLM to fill it in?

That's djoc. It's a document intelligence pipeline that turns unstructured files — scanned receipts, PDFs, photos of handwritten notes, voice memos — into structured JSON. OCR and language models do the heavy lifting. The interesting part is the abstraction: a schema and a prompt are all you write. The pipeline handles everything between the raw file and the validated output.

## The Processor Model

The core of djoc is the processor. A processor is a Pydantic schema paired with a configuration. You define what data you want to extract (the schema), which file types to accept, which OCR engine to use, and a prompt that tells the language model what to look for. That's it.

You don't write extraction logic. You don't write file parsers. You don't call the LLM yourself. The pipeline reads your schema, pulls text out of the document, hands the text and your prompt to whichever language model is configured, and validates the response against your types.

This separation — what you want vs. how to get it — is the whole design. It's a declarative pattern: you describe intent, the system handles execution. The schema is the contract between you and the pipeline. Pydantic gives you typed output and validation for free. The LLM provider isn't baked into the processor config; it's injected at registration time, so processors stay provider-agnostic. Want to swap from a local model to a cloud one? Change an environment variable, not your processor.

Adding a new document type is one file and one registration call. There's a scaffolder script, but the point isn't the tooling — it's that the abstraction is simple enough to make scaffolding trivial. That moment when a new processor just works — schema in, structured data out, no glue code — is what made this project satisfying to build.

## The Pipeline

Every layer in the pipeline exists because of a specific design decision, not because it was in a template.

**File routing** is convention-based. Copyparty watches inbox folders, and the directory name maps directly to a processor. Drop a file into `/vault/+.inbox/receipts/` and the receipt processor picks it up. No routing config, no dispatch table — just directory names. I chose Copyparty because it gives you a web UI, WebDAV, and file watching without writing any of that yourself.

**Text extraction** sits behind a common interface. PaddleOCR, LightOn for images and PDFs. Whisper for voice memos. The processor config declares which engine to use; the pipeline doesn't care which one it is.

**LLM extraction** works the same way. The extracted text, your prompt, and your Pydantic schema go to whichever provider is configured — Ollama for local inference, OpenRouter for cloud models. Same interface, completely swappable.

**Storage** is PostgreSQL, one table per processor. The schema defines the columns.

There's a second ingestion path through OpenClaw, which lets you send documents via WhatsApp. Snap a photo, send it, and it lands in the same inbox that Copyparty watches. The pipeline doesn't care where files come from — that's the point.

## The Self-Hosted Stack

The pipeline layers above all run as Docker Compose services.

Everything runs via Docker Compose. One command starts the full pipeline: Copyparty for file uploads, Prefect for workflow orchestration, PostgreSQL for storage, pgweb for browsing results, and optionally Ollama for local LLM inference.

Running Ollama locally means sensitive documents never leave my machine. OpenRouter is there as a fallback when I need a larger model. Prefect gives me observability — every flow run, every failure, every retry is visible in the UI. If something breaks, I can see exactly where.

One small thing I'm proud of: the project uses git worktrees for parallel development, and all worktrees share one Docker Compose stack via a fixed project name. Switching between branches doesn't mean spinning up parallel infrastructure. The database persists, but the running code always reflects whichever worktree last started the stack.

The philosophy is pragmatic: I wanted full control over my documents and my data, and composing existing tools was cheaper than building everything from scratch.

## Honestly

I don't receive enough documents to justify any of this automation. Djoc isn't solving a burning problem I have — I built it because the design challenge was interesting. How simple can you make the interface between a messy document and structured data?

The repo is private — it's not mature enough to share publicly, and finding the use case that would push it there is part of what makes the problem interesting.

What I got out of it was the engineering: composing tools into a coherent stack, designing an abstraction that stays out of the way, and making the pipeline disappear behind a schema definition. Sometimes the project is the point.
