## What If the Schema Was the Whole Thing?

Most document processing code is glue. You write a parser for this format, a normalizer for that one, custom extraction logic for every new document type. Djoc flips that: you define a Pydantic schema, a prompt, and a small config (file types, OCR engine), and the pipeline routes your document through text extraction and an LLM to fill in the schema.

It turns unstructured files — scanned receipts, PDFs, voice memos — into structured JSON. OCR and language models do the extraction. You write the schema and the prompt; the pipeline handles everything between the raw file and the validated output.

## The Processor Model

A processor is a Pydantic schema paired with a config dict. The schema defines what to extract. The config declares accepted file types, which OCR engine to use, and a prompt for the LLM. The pipeline reads your schema, pulls text out of the document, hands the text and your prompt to the configured language model, and validates the response against your types.

You don't write extraction logic, file parsers, or LLM calls. The LLM provider is injected at startup from environment variables, so processors stay provider-agnostic. Swap from a local model to a cloud one by changing an env var.

Adding a new document type is one Python file in `processors/`. Auto-discovery picks it up on restart.

## The Pipeline

**File routing** is convention-based. A file server watches inbox folders, and the directory name maps to a processor's `tool` field. Drop a file into `/vault/+.inbox/receipts/` and the receipt processor picks it up.

**Text extraction** sits behind a common interface. OCR for images and PDFs, speech-to-text for voice memos, direct parsing for text formats. The processor config declares which engine to use.

**LLM extraction** works the same way. The extracted text, your prompt, and your Pydantic schema go to whichever provider is configured — local or cloud.

**Storage** is one table per processor. The schema defines the columns.

There's a second ingestion path through a chat gateway (WhatsApp/Telegram). Send a photo and it lands in the same inbox.

## The Self-Hosted Stack

Everything runs via Docker Compose. Local inference means sensitive documents never leave my machine; a cloud provider is there when I need a larger model. The orchestrator (Prefect) gives observability — every flow run, failure, and retry is visible in a UI.

The project uses git worktrees for parallel development. All worktrees share one Docker Compose stack via a fixed project name. The database persists across worktree switches, but the running code always reflects whichever worktree last started the stack.

The pipeline described above used a custom Python router — a function that matched directory names and file extensions to processors. It worked, but routing decisions were invisible. No event trail, no per-processor concurrency control, and adding observability meant building it myself.

The refactor replaced that with Prefect's native event system. Copyparty fires an HTTP webhook that posts to the Prefect events API — no SDK needed in the file server container. Prefect automations match those events to per-processor deployments. The custom routing code is gone.

## Honestly

I don't receive enough documents to justify this automation. I built it because the design challenge was interesting: how simple can you make the interface between a messy document and structured data?

The repo is private. What I got out of it was composing tools into a coherent stack and designing an abstraction that stays out of the way.
